# Cobertura funcional API GACOR/DERCAS

## Evidencia de autorización por rol

La matriz fue aprobada para fixtures locales. `test:integration:domain-writes` valida el caso sin grants (403 en operaciones protegidas), asigna temporalmente `PILOTO_BRIGADA` con los cinco permisos propuestos (200 en vehículo/asignación propios; 403 en vehículos administrativos) y confirma `GET /users/me/access`. Tras la prueba `usuario_rol`, `rol_permiso`, asignaciones, brigadas, vehículos, usuarios y dispositivos quedaron en cero en `dercas_journey_test`. Esto no constituye seed permanente ni autorización para otra base.

Actualizado: 2026-10-16. La matriz por dominio de este documento es complementaria. El inventario exhaustivo de las 72 operaciones, estado individual, permiso, alcance, tablas SQL, evidencia y huecos está en [GLOBAL_API_AUDIT.md](GLOBAL_API_AUDIT.md#inventario-completo-por-endpoint). Los resultados actuales de validación y la rúbrica del porcentaje funcional también están allí; los conteos históricos que aparecen más abajo no sustituyen esos resultados actuales.

## Resumen vigente del árbol

En 2026-10-16: unitarias 259/259; typecheck/lint/build/OpenAPI/contrato estático SQL pasan; `domain-writes` pasa 3/3 en tmpfs; integración de lectura 12 pasan, 3 omitidas y 1 falla en la expectativa de conteo de constraints de la prueba. Las consultas posteriores a `domain-writes` confirmaron cero fixtures en tablas verificadas.

## Leyenda de estado

- **IMPLEMENTADO Y VERIFICADO**: comportamiento probado con evidencia apropiada al alcance (para afirmar compatibilidad DB hace falta integración real).
- **IMPLEMENTADO SIN VERIFICACIÓN REAL**: ruta/código y/o tests unitarios existen; comportamiento PostgreSQL real no probado.
- **PARCIAL**: parte de la lectura/escritura o flujo existe y falta el resto.
- **AUSENTE**: no se encontró endpoint/caso de uso en el árbol inspeccionado.
- **BLOQUEADO**: requiere decisión, contrato externo, permiso aprobado o instancia aislada que no está disponible.

Quedó verificado el flujo HTTP con fixtures auto-creados en DB desechable: login concurrente 201/409, refresh/replay, revoke/logout, perfil y acceso propios sin secretos, grants locales aprobados para `PILOTO_BRIGADA`, autorización positiva/negativa, aislamiento por objeto con un segundo piloto de iguales grants, ciclo de jornada, combustible e incidencia. En combustible e incidencia, dos POST simultáneos con el mismo UUID retornan el mismo recurso; un payload distinto con ese UUID retorna 409, y consultas de conteo confirman una fila por operación (combustible también crea una sola lectura de odómetro). El servidor HTTP usa el rol PostgreSQL restringido `dercas_api_runtime`; el pool de fixtures está separado. El E2E confirma que payloads inválidos de jornada/combustible/incidencia devuelven 400 sin insertar filas, y que las listas propias del segundo piloto no revelan recursos ajenos. El guard resuelve sesión y permisos efectivos en una consulta SQL. Las respuestas HTTP incluyen `Cache-Control: no-store`. Cinco handlers que documentan respuesta nullable normalizan el resultado nulo como JSON `null` explícito para alinear el cuerpo con OpenAPI. La aprobación de matriz se limita a fixtures locales y no autoriza seeds en otras bases. OpenAPI expone 72 operaciones: 70 schemas descriptivos y dos endpoints 204 sin cuerpo; E2E sin DB verifica `/docs`, `/docs/openapi.json` y liveness/readiness. El verificador contrasta permisos y esquemas documentados contra código y SQL.

## Inventario del esquema SQL y trazabilidad

Los nombres y definiciones siguientes son lo que declara el archivo SQL versionado, no el catálogo real de un servidor. Claves foráneas y constraints deben cotejarse con DDL en [GACOR_DERCAS_PostgreSQL_v3_GPS.sql](docs/GACOR_DERCAS_PostgreSQL_v3_GPS.sql); no se alteraron. `PK`, `FK`, `UNIQUE`, `CHECK`, índices parciales y triggers son integridad de persistencia y no generan por sí mismos rutas REST.

## Bloqueos para integración funcional

1. Se verificó una instancia efímera para esta ejecución. Para repetir integración debe recrearse y volver a verificar el destino; no quedó servicio de pruebas persistente.
2. La propuesta `PILOTO_BRIGADA` se aprobó para fixtures E2E locales; las asociaciones generales de roles y permisos siguen pendientes en `PERMISSION_MATRIX.md`. No ampliar operaciones sensibles inventando permisos.
3. Ingesta GPS requiere corregir la incompatibilidad confirmada en el DDL oficial; después requiere protocolo de hardware y políticas de timestamps/deduplicación/frecuencia.
4. Evidencia necesita backend de almacenamiento y política de acceso/retención.
5. Operación de gabinete y estados de préstamo dependen del contrato del ESP32/operación física.
6. Reportes necesitan alcance y permiso aprobado.
