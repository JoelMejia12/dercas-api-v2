# Hoja de ruta de implementación

## Prioridad de auditoría global (2026-10-16)

La secuencia a continuación sustituye las prioridades anteriores cuando exista conflicto. El inventario completo y los criterios de avance están en [GLOBAL_API_AUDIT.md](GLOBAL_API_AUDIT.md). El cierre HTTP de jornadas ya se ejecutó en la base efímera indicada en el checkpoint de trabajo; el siguiente bloque propuesto aún requiere autorización:

1. **Lecturas HTTP de movimientos de brigada**: cubrir `GET /movements/me/assigned`, `/assigned/open` y `/assigned/:id` con respuesta positiva, vacío, 401/403 e ID ajeno/inexistente. Es independiente de escrituras; contrato, permiso `VEHICULO_USAR_ASIGNADO` y consultas de propiedad ya existen. Requiere fixture piloto aprobado, asignación/jornada local y DB `tmpfs`; solicitudes con `dercas_api_runtime`, lecturas de verificación y cleanup administrativo.
2. **Reparar test de catálogo**: alinear su conteo de constraints con la forma real del SQL (la prueba exige >10, mientras el parser captura dos nombres); no alterar el SQL para satisfacer la expectativa. Repetir integración sobre base recién cargada.
3. **Cerrar RBAC/ACL por contrato**: que responsable defina rol→permiso→alcance y operadores definan grants de DB runtime por ruta. No sembrar asociaciones automáticamente. Probar positivo/negativo, propiedad, respuestas y mínimo privilegio con `dercas_api_runtime`.
4. **Positivos HTTP por módulo**: vehículos, asignaciones, odómetro, préstamos, mantenimiento, emergencias, alertas/notificaciones, gabinete y lecturas GPS. Para cada endpoint cubrir auth, permisos, DTO, datos/ownership e inexistente; concurrency para escrituras.
5. **Desbloquear GPS**: requiere autorización explícita de cambio SQL y revisión responsable. Alinear `fn_notify_realtime` con identidad de fila de `ultima_posicion_gps`; cargar SQL corregido en instancia nueva y probar notify/rollback/partición antes de conectar protocolo hardware. La UI/UX actual prohíbe GPS permanente/rutas en vivo y solo permite ubicación puntual durante emergencias; seguimiento temporal requiere una decisión de producto independiente.
6. **Definir y completar operaciones administrativas**: aprobación y ciclo físico de préstamos/gabinete; mantenimiento global y transiciones; provisioning/rotación/revocación de dispositivos; eventos y gestión RBAC.
7. **Diseñar evidencias, reportes y auditoría**: requiere decisiones de almacenamiento, clasificación/retención, destinatarios, permisos y auditoría antes de endpoints.
8. **Retención y preparación de release**: worker con rol separado, dry-run/restore/auditoría, backups, TLS/proxy/rate limits, CI/cargas/operación.

Cada bloque tiene aceptación concreta en la sección “Plan por bloques y aceptación” de `GLOBAL_API_AUDIT.md`. Ningún bloque autoriza recrear el esquema, modificar bases compartidas ni conceder permisos no aprobados.

La auditoría completó verificaciones aisladas con PostgreSQL 17/PostGIS en `tmpfs`, SQL oficial sin edición y flujos HTTP autenticados. El E2E usa `dercas_api_runtime`, un rol no superusuario con UPDATE por columna y ACL restringida, para auth, jornada, combustible e incidencia; el resto de las consultas de repositorio y fixtures siguen usando el pool administrativo del contenedor. El responsable aprobó la [matriz de autorización](PERMISSION_MATRIX.md) para fixtures E2E locales: grants temporales `PILOTO_BRIGADA` pasan pruebas positivas, negativas y de aislamiento entre usuarios, y se limpian. No se han aprobado asociaciones generales ni grants en bases compartidas. Siguen pendientes verificar ACL mínima en los demás módulos, cubrir los demás flujos HTTP y seguridad de despliegue.

## Dependencias estructurales

La política de roles y propiedad precede a ampliar rutas administrativas; el entorno PostgreSQL aislado precede a las pruebas reales de triggers/views/concurrencia; el protocolo de hardware precede a ingesta GPS o comandos de gabinete; política de retención precede a cualquier purga. SQL actual debe preservarse y versionarse mediante un plan aprobado, no reescribirse en esta fase.
