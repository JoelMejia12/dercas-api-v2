Fecha de revisión: 2026-10-16. La auditoría endpoint por endpoint actual, los resultados reales de este árbol y el avance calculado están en [GLOBAL_API_AUDIT.md](GLOBAL_API_AUDIT.md). Este documento conserva los hallazgos anteriores; los conteos y resultados de pruebas del bloque actual sustituyen el baseline histórico que sigue citado en secciones abajo.

## Resultado actual de auditoría global

- Inventario de 72 operaciones HTTP con estado, permiso/alcance, entidades SQL y pruebas/gaps por endpoint: [GLOBAL_API_AUDIT.md](GLOBAL_API_AUDIT.md#inventario-completo-por-endpoint).
- GPS fue reproducido con SQLSTATE `42703`; autorización RBAC no tiene asignaciones seed; módulos y dependencias pendientes, journeys y rúbrica funcional (49%) están documentados en el informe global.
- En el árbol de 2026-10-16: `npm test` 66/66 archivos y 259/259 casos; typecheck, lint, build/OpenAPI y `sql:check` pasan. Integración de dominio 3/3 pasa en tmpfs. No se modificó el test ni el SQL.

## Estado actual comprobado

- Proyecto privado `dercas-api` (0.1.0), Node >=22, NestJS 11, TypeScript, Express, `pg`, PostgreSQL directo con consultas SQL parametrizadas. Validación vía `class-validator`; Argon2, Helmet y Vitest están declarados.
- `src/` tiene módulos para autenticación, usuarios, vehículos, préstamos, asignaciones, movimientos, jornadas, combustible, odómetro, mantenimiento, incidencias, alertas/notificaciones, gabinete, GPS, salud, reportes y evidencia; la mayoría de acceso SQL se encapsula en repositorios.
- Hay `docs/GACOR_DERCAS_PostgreSQL_v3_GPS.sql`, además de documentación de integración. No hay ORM ni directorio de migraciones detectado. El SQL es un script transaccional de inicialización, no se ha comprobado aplicado.
- Hay controladores de lectura y algunas escrituras ya implementadas; por ejemplo, autenticación, solicitudes de préstamo, combustible, mantenimiento, incidencias y recepción GPS a nivel de repositorio. El controlador GPS expone lecturas solamente. Evidencia y reportes no muestran controladores/servicios de funcionalidad en el inventario inspeccionado.
- El seed SQL incluye seis roles y 23 permisos. Los códigos usados por los guards aparecen en el catálogo, pero no hay inserción de filas `rol_permiso`; la asignación efectiva depende de aprovisionamiento externo no descrito. No se puede inferir una matriz rol→permiso.
- `main.ts` aplica prefijo `/api/v1`, Helmet, `ValidationPipe` global con `whitelist` y rechazo de campos desconocidos, filtro de excepción, request ID, `Cache-Control: no-store` y logging saneado. Configuración exige secreto de acceso de al menos 32 bytes antes de abrir HTTP. Readiness consulta la DB mediante `SELECT 1`.
- `DatabaseService` usa `pg.Pool`, consultas parametrizadas, transacciones explícitas y contexto transaccional `app.user_id` / `app.ip` para auditoría. Pool máximo 10; `search_path=gacor,public`. `PGSSL=disable` se conserva para desarrollo/test; ahora `NODE_ENV=production` con DB configurada exige `verify-full` y falla antes de abrir HTTP si falta.
- Autorización HTTP usa permisos efectivos consultados desde `roles`/`permisos`, guards y consultas filtradas por usuario en numerosos endpoints. No se encontró una política RLS en el SQL.
- Existen pruebas Vitest unitarias de módulos y guards y una suite optativa de PostgreSQL. El harness HTTP de autenticación se activó solo con fixture aleatorio reservado en la DB efímera.
- Baseline local: `npm test` aprobó 65 archivos/257 pruebas; lint, typecheck, build, `npm run openapi:check` y `npm audit --omit=dev` terminaron correctamente. OpenAPI publica 72 operaciones; el verificador requiere 70 respuestas descriptivas, dos 204 sin cuerpo y no acepta schemas genéricos opacos; verifica Bearer en toda ruta no pública, permiso en escrituras salvo operaciones de sesión propia, códigos contra catálogo SQL, creación 201 y paginación. La integración de lectura más reciente se repitió el 2026-10-15 en una instancia recién creada desde `postgis/postgis:17-3.5`: `dercas-gacor-fresh-audit`, `dercas_fresh_test`, `127.0.0.1:32770`, `tmpfs` 1 GB y sin mounts persistentes. Se cargó el SQL oficial sin edición; PostgreSQL 17.5/PostGIS; 6 roles, 23 permisos y cero asociaciones. `npm run test:integration` aprobó 12 y omitió 3 pruebas de fixture opcional en 3 archivos. Incluye el servidor HTTP OpenAPI sin DB, lecturas PostgreSQL, catálogo, PostGIS, objetos, triggers/índices y rollback. Una corrida anterior de lectura aprobó 12/12 con fixture efímero de auth: login concurrente 201/409, refresh/replay/revoke/logout, perfil sin hashes y aislamiento de alertas/notificaciones. La instancia fresca no corrió suite de escrituras.

- Una segunda base local `dercas_journey_test` en contenedor `tmpfs` ejecutó pruebas de escrituras aisladas (3/3 casos): inicio, reintento idempotente, competencia con otro UUID bloqueada sin filas parciales, regresión de odómetro rechazada por trigger, cierre y reintento de jornada; sesión activa sin roles retorna permisos vacíos; solicitud/reintento concurrente, conflicto activo y aislamiento por propietario de préstamo; reporte/reintento concurrente, conflicto de payload, historial y ownership para combustible; creación/replay concurrente, payload conflictivo y ownership de incidencia; dos órdenes de mantenimiento concurrentes resultan en una inserción y un conflicto por índice parcial, y trigger sincroniza estado del vehículo; E2E HTTP de sesión, DTO, auth y ownership. En la última corrida, el E2E HTTP también verificó dos POST concurrentes con el mismo UUID para combustible e incidencia: ambos devolvieron el mismo recurso, el payload diferente dio 409 y los conteos SQL fueron una carga, una lectura de odómetro y una incidencia. La prueba confirmó que GPS falla por el trigger oficial `fn_notify_realtime` en `ultima_posicion_gps` (SQLSTATE `42703`). El repositorio prepara deduplicación por UUID con advisory lock, pero no se puede validar funcionalmente hasta corregir el trigger. El pool de fixtures de dominio usa superusuario local; el proceso HTTP de los flujos E2E usa el rol restringido `dercas_api_runtime`. Tras aprobarse la matriz para fixtures locales, el E2E comprueba los cinco permisos propuestos de `PILOTO_BRIGADA`, operaciones propias, denegación administrativa y aislamiento frente a otro piloto; grants, filas fixture y bitácora terminaron en cero. Esto valida el subconjunto HTTP ejercitado y no las ACL de todos los módulos. No es aprobación para sembrar asociaciones generales.

## Hechos y riesgos con evidencia

`npm run sql:check` verifica estáticamente que las 51 referencias `gacor.*` y los 11 casts de enums encontrados en TypeScript tengan declaraciones en el SQL oficial. Es solo una comprobación de nombres: no demuestra compatibilidad de columnas/tipos, permisos, triggers desplegados ni ejecución de cada consulta.

| Hallazgo | Evidencia y valoración |
|---|---|
| La DB operativa no está verificada | `DatabaseModule` construye el pool desde el entorno. Sí se verificaron consultas y flujo HTTP contra una DB efímera PostgreSQL 17/PostGIS; no se comprobó DB externa/operativa ni TLS. HTTP E2E usa identidad no superusuario con ACL restringida para los flujos cubiertos; no se certifica ACL de los demás módulos/despliegue. |
| El código asume el SQL esperado | Repositorios nombran tablas/vistas y castea tipos explícitos; p.ej. `gacor.vw_vehiculos_administrativos_disponibles`, `vw_estado_mantenimiento`, `vw_mapa_vehiculos_tiempo_real`, `vw_estado_dispositivos` y `vw_retencion_gps`. El script define estas vistas, pero eso solo prueba presencia en el archivo, no existencia en la DB instalada ni privilegios. |
| El seed no asigna permisos a roles | Inserta seis roles y 23 permisos, incluidos todos los códigos requeridos por guards, pero no se encontró `INSERT` a `rol_permiso`. Una base inicializada solo con estos datos no otorga permisos efectivos; el mapeo debe decidirlo el responsable. |
| La ruta administrativa de gabinete falla cerrada con grants vacíos | En la instancia aislada sin filas en `usuario_rol`/`rol_permiso`, login HTTP produce principal sin permisos y `GET /cabinet` responde `403`. Esto verifica denegación sin grants, no que una asignación de rol concreta sea correcta. |
| Modelo SQL tiene invariantes de negocio útiles | Enums para estados/tipos; FK y CHECK; índices únicos parciales para sesión abierta por dispositivo, asignación activa por vehículo/piloto, movimiento abierto por vehículo/usuario, préstamo por vehículo no finalizado/cancelado y orden bloqueante por vehículo. Mantenerlos como autoridad ante concurrencia; comprobar DDL aplicado y mapeo de errores SQLSTATE. |
| Carrera de login concurrente detectada y mitigada | Una integración HTTP simultánea con `FOR SHARE` reprodujo respuestas `201`/`500` en lugar de `201`/`409`. El diagnóstico HTTP fue genérico y no confirmó el SQLSTATE causal; el orden de bloqueos previo podía formar una espera circular entre sesión/dispositivo y actualización de usuario. El repositorio ahora bloquea usuario/dispositivo con `FOR UPDATE`; la repetición devolvió una sesión y un conflicto `409`, sin sesión abierta residual. Esto cubre un escenario y no equivale a carga o concurrencia de flujos vehiculares. |
| Respuesta de login no revela existencia de usuario en el caso probado | Integración HTTP comparó fallo por contraseña incorrecta para email existente con email inexistente; ambos devolvieron mismo status/código/detalle. No es evaluación de tiempo ni de fuerza bruta/rate limit. |
| Status de logs HTTP corregido en errores | El E2E de DTO inválido mostró que `RequestLoggingInterceptor` registraba el status por defecto del controlador (`201`) antes de que `AppExceptionFilter` enviara el `400`. Ahora registra completitud al evento HTTP `finish`, y registra `close` anticipado como respuesta incompleta. Prueba unitaria verifica status final y no duplicar logs; la integración volvió a observar únicamente status `400` para ambas entradas de error. |
| GPS requiere validación operativa adicional | SQL declara `posiciones_gps` particionada por `fecha_hora_servidor`, partición DEFAULT, claves compuestas, tipos PostGIS, índices GiST/BRIN y trigger que mantiene última posición. El repositorio de inserción existe, pero no se observó una ruta HTTP de ingesta; protocolo de hardware/auth separado sigue pendiente. Funciones de archivo/purga pueden alterar o eliminar datos/particiones. |
| Ingesta GPS falla contra el SQL oficial cargado | Se ejecutó `GpsPositionRepository.insert()` en la DB `tmpfs`. El trigger de posición inserta en `ultima_posicion_gps`, cuyo trigger `trg_ultima_gps_notify` llama `fn_notify_realtime`; la función intenta leer `NEW.id`, columna inexistente en esa tabla. PostgreSQL devuelve SQLSTATE `42703` y revierte posición, última posición y actualización del dispositivo. El SQL oficial no se modificó y no se deshabilitaron triggers. Bloquea la ingesta hasta corrección autorizada del DDL. |
| Esquema de autenticación tiene datos sensibles | `usuarios.password_hash`, `dispositivos.device_token_hash` y `sesiones_dispositivo.refresh_token_hash` constan en SQL. Revisar proyecciones y ACL de cada ruta/rol; no se exponen estos valores por diseño visible de consultas seleccionadas, pero no se certifica toda respuesta sin revisión completa. |
| El rol PostgreSQL puede tener acceso transversal | Seguridad por fila recae principalmente en guards y filtros SQL; el esquema no declara RLS. Una consulta nueva sin predicado de propiedad puede cruzar usuarios aunque HTTP autorice el permiso general. Aplicar mínimo privilegio y pruebas negativas por dueño/rol. |
| Riesgo de concurrencia | Jornada, préstamo, combustible e incidencia probaron reintentos concurrentes con el mismo UUID; además, una segunda jornada con UUID distinto se rechazó mientras existía movimiento abierto y se verificó rollback sin filas parciales. Mantenimiento probó colisión del índice parcial. Falta carga, deadlocks y competencia entre usuarios/vehículos distintos. |
| Auditoría depende de trigger y contexto | `transaction()` asigna `app.user_id`/`app.ip` local a transacción; SQL define triggers de auditoría. Confirmar que cada escritura auditada usa esta transacción y que rollback revierte tanto cambio como bitácora. Consultas simples fuera de ella no llevan ese contexto. |
| Eventos de sesión no generan bitácora en el DDL observado | El trigger genérico `fn_auditar_cambios` solo se instala en la lista explícita de tablas, que excluye `sesiones_dispositivo`; en la DB efímera solo está `trg_sincronizar_sesion_dispositivo`. `createSession`, `rotateRefresh`, `revoke` y `closeSession` no escriben eventos manuales en `bitacora`. Login, rotación, cierre/revocación y limpieza por expiración carecen así de auditoría durable. Definir con el responsable los eventos/campos de auditoría antes de implementar escritura manual, sin registrar hashes de tokens. |
| Política TLS de producción | Configurar `NODE_ENV=production` con PostgreSQL y `PGSSL` ausente o `disable` falla con error genérico de configuración antes de abrir HTTP. Para operar, el responsable debe instalar certificado/CA confiable y configurar `verify-full`; el ambiente de pruebas local puede usar `disable`. |
| Sin despliegue reproducible confirmado | Se encontraron scripts npm, pero no se detectaron Dockerfile, Compose, workflow CI ni migraciones. No implica que no existan fuera del repositorio inspeccionado. |
| Índices/performance validados solo de forma limitada | Se ejecutó `EXPLAIN (COSTS OFF)` para búsqueda GPS por `uuid_operacion` en la DB efímera; el plan usa `Merge Append` y los índices únicos locales de las particiones. No demuestra rendimiento con volumen real ni índices/plans de otras consultas; no se ejecutaron mediciones ni carga. |

## Contraste código–SQL

- Coincidencia estructural aparente: las referencias SQL observadas usan el esquema `gacor`, y el script define las entidades y vistas principales requeridas. Es una coincidencia textual, no una comprobación de compatibilidad desplegada.
- Repositorios acceden a enums con casts (`gacor.estado_*_enum`) y vistas de disponibilidad, mantenimiento, GPS y dispositivos. La integración ejecutó consultas de lectura y comprobaciones de objetos en la DB efímera; jornada, préstamo, combustible, incidencia y mantenimiento cuentan con verificaciones de escritura delimitadas; GPS confirmó el error de un trigger, no un flujo exitoso.
- En la verificación HTTP se detectó que dos access JWT emitidos en el mismo segundo podían ser idénticos. Se corrigió añadiendo `jti` aleatorio, con pruebas de emisión en el mismo segundo y compatibilidad de tokens válidos anteriores sin `jti`.
- El guard consulta estado vigente de sesión y permisos efectivos en PostgreSQL en cada request. Se consolidó en una consulta `LEFT JOIN` para que ambas decisiones compartan el snapshot SQL y evitar un segundo viaje a la base. La integración confirma primero permisos vacíos; tras aprobación para fixtures locales, un E2E asigna temporalmente `PILOTO_BRIGADA`, confirma sus cinco permisos, obtiene 200 en lecturas propias y 403 en la lectura administrativa. También verifica inicio/replay/finalización de jornada (201/201/200), reporte/lectura de combustible (201/200) e incidencia/detalle propio (201/200), con 403 para las escrituras antes del grant. Un segundo principal con iguales grants no puede leer los IDs ajenos (404 jornada, combustible e incidencia). La limpieza deja vínculos, entidades y bitácora en cero. Esto no aprueba asignaciones generales en otra base.
- El servidor HTTP de integración ya no usa el superusuario: se conecta como `dercas_api_runtime`, un rol local sin superusuario, herencia, membresías, creación de objetos/base/roles, `DELETE` ni lectura de gabinete. Sus privilegios UPDATE son column-scoped, incluidos los mínimos para `FOR UPDATE`; el preflight prueba que no puede cambiar hashes de credenciales o campos de propiedad y que no tiene UPDATE de tabla completa. El E2E sigue pasando con esos grants estrechos. Esto valida el conjunto de flujos ejercitados, no ACL mínima para todos los módulos de la API.
- El E2E cruzado añadió validación DTO bajo la identidad runtime: jornada, combustible e incidencia inválidas devuelven 400 y se verifica que no dejaron filas. También expuso que Nest convertía los resultados `null` en cuerpos HTTP vacíos pese al schema OpenAPI nullable; `JsonNullInterceptor` normaliza los cinco handlers nullable a JSON `null`, manteniendo no-null inalterado. El test de integración confirma ese contrato en las listas sin recursos.
- El contrato de IDs se conserva en general como texto al seleccionar `BIGINT`; importes/odómetros `NUMERIC` requieren conservar precisión (la integración documenta este requisito). Debe sostenerse como regla de serialización de API.
- SQL incluye `evidencias`, `bitacora`, jornadas y procesos de archivo/restauración GPS. El estado funcional de evidencia/reportes y de operaciones administrativas GPS no se demuestra por el nombre del módulo; auditar rutas completas antes de prometer cobertura.
- El acceso de escritura a posiciones GPS está en un repositorio (`gps-position.repository.ts`), pero no está publicado por el controlador y falla por el trigger `NEW.id` incompatible del DDL observado. La API no demuestra recepción autenticada de dispositivos ni supervisión de latidos.
- Los enums/catálogos SQL son más amplios que las operaciones HTTP visibles. La cobertura exacta de transiciones y catálogos debe definirse con responsables del dominio y trazarse contra cada flujo.
- El SQL contiene funciones de retención/purga y triggers laterales; la API no debe replicar sus cálculos. No hay evidencia de que el rol de aplicación tenga permisos ni de que esas funciones hayan sido instaladas.

## Seguridad y verificación pendientes

No se examinó despliegue ni se leyó ningún secreto. No hubo conexión a DB compartida.
